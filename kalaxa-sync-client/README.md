# Kalaxa Sync Client — v0.2.1 (اکستنشن اسکچاپ)

> 📘 راهنمای مصور: `docs/guide-fa-sync-client.pdf`

حلقهٔ همگام‌سازی را می‌بندد: پیاده‌سازی HTTP قرارداد `SyncPort` (D-SYNC-3) علیه افزونهٔ
وردپرسی **kalaxa-sync** روی kalaxa.ir. عمداً «مخزن جدا» است تا هستهٔ آفلاین Kalaxa
بدون کد شبکه بماند.

## پیش‌نیازها
- پلاگین اصلی Kalaxa **v3.1.0+** نصب و فعال.
- افزونهٔ وردپرسی kalaxa-sync v0.1.0+ روی سایت + کاربر با Application Password
  (توانایی `kalaxa_sync_write` برای این دستگاه).
- HTTPS اجباری است — کلاینت روی http قاطعانه کار نمی‌کند.

## نصب و استفاده
پوشه را داخل Plugins اسکچاپ بگذارید (یا rbz بسازید). منو:
**Extensions ← Kalaxa Sync**: «تنظیمات…» (آدرس/کاربر/اپ‌پسورد) → «وضعیت سرور» →
«Push به سرور» / «Pull از سرور».

رفتار واگرایی (D-SYNC-2 — LWW دستی):
- Push وقتی سرور از آخرین هم‌نظری شما جلوتر باشد، اول هشدار می‌دهد؛ Yes = بازنویسی سرور.
- Pull وقتی تغییر محلی sync نشده دارید، اول هشدار می‌دهد؛ Yes = بازنویسی مدل.
- محتوای یکسان در هر دو جهت بدون نوشتن، «هم‌نظر ✔» گزارش می‌شود.
- شمارندهٔ revision و device_id در `%APPDATA%\Kalaxa\sync_client.json` نگه‌داری می‌شود.

## رفع باگ در v0.2.1 (کشف با اجرای واقعی بوت خارج از اسکچاپ)
- **(#۱۲ بحرانی برای این کلاینت):** هر ۲۵ ارجاع `UI` در `main.rb`/`client.rb` خالی نوشته
  شده بود؛ داخل تودرتوی `module Kalaxa` و با حضور هستهٔ اصلی (که `Kalaxa::UI` را تعریف
  می‌کند)، جستجوی lexical روبی `Kalaxa::UI` را جلوتر از `::UI` اسکچاپ می‌یافت →
  `NoMethodError` در همان `UI.menu` هنگام لود. یعنی کلاینت **دقیقاً وقتی پلاگین اصلی
  نصب بود** (تنها سناریوی کاربردی‌اش) اصلاً بالا نمی‌آمد؛ و بدون هسته، به مسیر fallback
  می‌رفت. همهٔ ارجاع‌ها `::UI` شدند (همان قرارداد `main.rb` پلاگین اصلی). اثبات: هارنس
  بوت stub — قبل از رفع کرش لود، بعد از رفع منوی ۴آیتمی واقعی + اجرای موفق `guarded()`.

## رفع باگ در v0.2.0 (ممیزی دوروندهٔ کد)
- **(#۳ متوسط):** `cmd_status`/`cmd_push`/`cmd_pull` قبلاً هیچ مهار خطایی نداشتند —
  برخلاف همه‌جای دیگر این اکوسیستم. مسیر واقعی رخداد: سند میراثی v1 با `thickness:null`
  در `NoMethodError`ی می‌ترکید که `Kalaxa::Error` نبود و بدون مهار مستقیم به کاربر
  می‌رسید. حالا هر سه دستور با `guarded()` پوشیده شده‌اند — هر خطای غیرمنتظره پیام فارسی
  می‌دهد، نه کرش خام.
- **(#۴ متوسط):** `HttpSyncPort#pull` مسیر خام را بدون بررسی JSON بودن `ok:true` گزارش
  می‌کرد؛ حالا مثل مسیر غیرخام اعتبارسنجی می‌شود.
- **(#۱۱ کم):** `decide_pull` یک حالت `:safe` مرده داشت (هرگز قابل‌دسترس نبود). حالا با
  ردگیری واقعیِ `last_synced_checksum` (نه فقط revision)، اگر سند محلی از آخرین sync
  موفق دست‌نخورده مانده باشد، Pull بدون پرسش انجام می‌شود — اثبات واقعی، نه حدس.
  `sync_client.json` حالا چک‌سام را هم کنار revision نگه می‌دارد.

## نکتهٔ امنیتی
Application Password به‌صورت متن ساده در فایل پیکربندی پوشهٔ دادهٔ کاربر ذخیره می‌شود.
برای این کلاینت یک اپ‌پسورد اختصاصی بسازید تا در صورت نیاز فقط همان را باطل کنید.

## راستی‌آزمایی (سهم شما — این محیط ساخت Ruby ندارد؛ Unverified تا اجرای شما)
```
ruby test/test_sync_flow.rb    ← ۱۱ تست منطق تصمیم Push/Pull (بدون اسکچاپ/شبکه؛ شامل :safe واقعی)
```
سپس سناریوی دستی سرتاسری روی استیجینگ:
۱) مدل با سند → Push (اولین بار، revision 1) ۲) Push دوباره → «هم‌نظر ✔»
۳) تغییر سند → Push → revision 2 ۴) از دستگاه/کپی دوم Push → هشدار واگرایی
۵) Pull روی مدل تغییرکرده → هشدار بازنویسی ۶) وضعیت سرور بین هر مرحله.
